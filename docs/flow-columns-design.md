# 流し組み（段落を列の中で流す）設計 — flow-columns ブランチ

作成: 2026-11-24 第91版の翌作業。本番（main / tateyomi.pages.dev）には触らない。
開発アドレス: https://flow-columns.tateyomi.pages.dev

## 問題（ユーザーの指摘が正本）

現行の組版は「段落ごとに新しい列から始める」。段落の最後の列は下半分が
空き、会話の多い本（短い段落の連続）では列の大半が空白になる。
紙の本の縦組みは段落が替わっても同じ列の中で流れ、字下げだけが入る。
この差が「ページ余白が多すぎる」の残件。

## 現行モデルの前提（洗い出し結果）

- `simulateSplit(para, off, colsAvail, ind)` は **1段落を新しい列の先頭から**
  模擬する。字下げは「その段落の最初の列の容量 −fs」で会計。
- `fillTierCore` は段落ごとに `sim.cols × colW` を予算から引き、段落の
  途中までしか入らない場合はそこで段を打ち切る。
- 描画は **1チャンク＝1段落断片＝1つの `<p>`**。縦書きのブロックボックスは
  列をまたげないため、段落の切れ目が必ず列の切れ目になる（これが模型と
  描画の一致点であり、同時に問題の発生点）。
- プローブ実測（probeSize/probeFits）は probeTier に同じチャンク列を
  描いて測る。接着検出（gluedChunkIdx）は「チャンクの `<p>` の実列数 ＞
  計画列数」を見る。splitTierChunks / topUpTier / heightSplitRepair /
  tierSlack もすべて「チャンク＝段落断片」の前提で書かれている。
- 位置・しおり・検索は段落（pi/off）基準で、チャンクには依存しない。
  ここは変更の影響を受けない。

## 新方式：列を計画の単位にする

### 計画（fillTierCore / simulateSplit の一般化）

- 模擬を「段落単位」から「流れ単位」に広げる。段落境界を跨いで列を
  継続する点を除き、禁則・追い込み・単語接着・ルビガードの規則は
  段落内部の現行ロジックをそのまま使う（列を割る位置の規則は変えない）。
- 段落の開始が列の途中にある場合、その列の残り容量の中で字下げぶん
  （fs）を消費してから本文を置く。段落開始がちょうど列頭に来た場合も
  字下げは入る（現行と同じ）。
- 列の区切りは段落境界でも起きてよい（段落の途中で列が満ちれば次列）。
  禁則は段落を跨がない（段落境界は常に切断可能位置）。
- 見出し・タイトル・挿絵・表・空行・改ページ／改段は従来どおり原子的
  に扱い、流れの対象は通常の本文段落の連続だけに限る。

### 描画（renderChunks）— 実装方式（2026-11-24 実装時に確定）

- 当初案の「1列＝1つの `<p>`」は、チャンク＝列に作り替えるため修復系
  すべてに手が入る。実装はより小さい手術にした：**段落の連続を1つの
  仮想段落として連結し、1チャンク＝1つの `<p>` のまま**、ブラウザ自身の
  折り返しに列の継続を委ねる。字下げは実単位（全角空白）として流れに
  差し込み、字下げの前後では列を割らないよう模擬側に禁止位置（glue）を
  渡す。
- チャンクには出所の対応表（flow：単位ごとの pi/off）を持たせ、位置の
  復元・列分割（splitTierChunks）・接着検出（gluedChunkIdx）を flow
  対応にした。tierSlack は計画列数で会計する。
- プローブ段も同じ renderChunks を通すため、実測の前提は保たれる。
- 個別修復（capMap / cols1Set）の対象段落を含む段は、従来の段落単位の
  割り付けに落とす（unglue は段落単位で収束する）。

### 会計（tierSlack / topUpTier）

- 段の占有幅は列数 × colW が基本になり、段落ごとの列数合算は不要に
  なる（むしろ単純化される）。
- topUpTier は「最後の列に次の断片を足す」操作に読み替える。

## 触らないもの

- 段落の解析（EPUB/青空/テキスト→段落列）、保存形式、位置・しおり・検索。
- 描画後監査（auditRenderedPages）と修復段（repairLevel / repairFloor）。
  DOM 実測ベースなので新方式でもそのまま最後の砦になる。
- 改ページ／改段、全面挿絵ページ、漫画モード、二段／一段の段組み構造。

## デグレリスクと対策

1. **文字欠けの再発**（最大リスク）：列 `<p>` の中でブラウザが予想外の
   折り返しをする型。→ プローブ実測は全段で継続。接着検出を列単位に
   読み替えて残す。描画後監査も残る。
2. **ルビ・傍点が列境界／段落境界に来るケース**：ルビ単位の原子性は
   描画側の inline-block 化（第86版）で担保済み。模擬側のルビガードは
   段落を跨ぐ列継続でも同じ位置に効かせる。
3. **組版速度**：模擬は単位を1回なぞる構造を維持する。長編（50万字級）
   で初回組版の時間を計り、現行比で悪化がないことを確認する。
4. **位置ずれ**：pi/off 基準は不変。ページ数は変わる（それが目的）が、
   読書位置は段落位置で復元される。

## 切り替えと戻し方

- 設定に組版方式の切り替え（流す／段落ごと）を置く。開発アドレス上で
  同じ本を両方式で見比べられるようにするためであり、マージ後も当面
  残す（問題が出たらその場で旧方式に戻せる）。
- ブランチ自体が切り捨て可能。本番は第91版のまま一切変わらない。

## 検証手順

1. 構文チェック＋開発アドレスへデプロイ（ブランチプレビュー）。
2. VM Chrome で開発アドレスを開き、コンソールエラーがないこと。
3. ユーザー実機・実際の本（刀語）で受け入れ：余白、文字欠け、ルビ、
   ページ送り、読書位置の復元。問題のあった 106〜109 ページ相当と
   会話の多い場面を重点的に。
4. 合格したら main へマージし、本番の版を上げる。切り替えスイッチは
   そのまま残す。
